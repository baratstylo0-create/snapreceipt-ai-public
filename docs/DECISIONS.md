## ADR-028 · Branch/user deactivation needs an audit trail + stronger confirmation — this must never silently lock out a real client
**Date:** 2026-07-14 · **Status:** Accepted (root-cause + guardrail recorded); code guardrail NOT YET BUILT — tracked here so it isn't lost.
**Context:** On the live Premala instance, the "Head Office" branch was soft-deleted via the Team page's Delete-branch action at some undetermined point. `softDeleteBranch()` (`lib/branches.js:184-195`) does exactly what it's designed to do: deactivates the branch, then deactivates **every user row tied to that branch_id** (no role filter) and revokes their sessions. Head Office happened to be the **real production admin's own branch** (`premala-admin`, created via `setup/provision.js`'s `provisionAdmin()`, which reuses `createBranch()` — an admin's "branch" is just their own home office row). The result: the client's real admin login silently stopped working, and the two staff display-names under it were deactivated too — surfaced as "a colleague's creds are invalid" and (separately, via the C6/C7 "My uploads" default) "admin has no data," discovered together, days apart from whenever the actual delete happened.
**Why this is worse than it looks:**
1. **No audit trail.** Neither `branches` nor `users` has a `deactivated_at`/`deactivated_by` column (confirmed in `schema.sql`) — there is no way to determine WHEN a deactivation happened or WHO did it, only that it happened. For a system holding a real client's financial data, this is a genuine gap.
2. **No "who does this affect" warning.** The Team page's delete action does not tell the admin, before they confirm, that a branch they're about to remove is tied to an active login (least of all their OWN admin login) — a single click, and the cascade in `softDeleteBranch` is immediate and silent.
3. **Fully recoverable, but only by someone who understands the cascade.** Reactivating is a simple `active: true` flip on the branch + affected users (the password hash is untouched, so the original credentials work again unchanged) — but nobody would know to do that without reading the code, since there's no in-app "recently deactivated, undo?" surface.
**Decision (the guardrail, to be implemented as a follow-up — NOT shipped in this ADR):**
- Add `deactivated_at` + `deactivated_by` (nullable) to `branches` and `users` — set by `softDeleteBranch`/`removeStaff`, so any future incident is instantly diagnosable ("when did this happen, and via which admin session").
- The Team page's Delete-branch confirmation must name what it will do BEFORE the click is committed — at minimum: "This will also deactivate N login(s): <names/roles>" — so an admin can't silently lock out a colleague (or themselves) by mistake.
- Consider a specific guard: deleting the branch tied to the **last active admin's own account** should require a harder confirmation (type-the-branch-name, or a second admin's sign-off) since it's the one case that can lock everyone out of the dashboard entirely.
**Consequences:** Until the guardrail above ships, this class of incident **can recur** on any client instance — it is a real, general risk, not specific to Premala or to anything from the 2026-07-13/14 deploy batch (confirmed: no PR from that batch touches `lib/branches.js`, `active` flags, or calls `softDeleteBranch`; this was a pre-existing manual Team-page action, unrelated to the day's code changes). Flagging this explicitly so it is treated as a launch-readiness item for any FUTURE client onboarding, not just a one-off cleanup for Premala.

## ADR-027 · Receipt images served under `/api/receipt/*` (not `/receipt/*`) to survive shared-tenant nginx
**Date:** 2026-07-13 · **Status:** Accepted (Owner: Jeevan). Runbook: MEMORY_LEDGER GOTCHA "CAN'T SEE RECEIPT IMAGES".
**Context:** The Premala box (`31.97.70.50`) is a **shared-tenant** nginx host serving this app (`:3005`) AND Barat's FrictionAI app (`:3001`). **Both apps serve receipt images at the identical path `/receipt/`.** nginx has a single `location /receipt/` block, and a `proxy_pass` can only target ONE backend — so the path can feed exactly one app. Pointing it at `:3001` fixes FrictionAI and breaks us; pointing it at `:3005` fixes us and breaks FrictionAI. This is not a transient bug — it is a **structural collision**, and it recurred **3× in a single day** (2026-07-12 once, 2026-07-13 twice) because every "fix" for one app silently un-fixes the other. Symptom: the dashboard shows *"This receipt has no photo available"* even though the image is present and downloadable in Storage. Diagnostic signature: `/api/*` → 401 (healthy) but `/receipt/*` → 404/502 (not reaching our app).
**Decision:** **Stop sharing the path.** Serve this app's receipt images under **`/api/receipt/by-id/:id` and `/api/receipt/:fileId`**, which ride the `/api/*` → `:3005` nginx catch-all (`location /`) that FrictionAI never claims (it only carves out `/handle`, `/web-chat`, `/falc-voice`, `/app/`). The legacy `/receipt/*` mounts are KEPT (backward-compat + any bot/external link), but the **frontend and all export links now use the `/api/receipt/*` form** (`activity.js`, `grid.js`, `routes/{excel,manageExport,statement}.js`). No nginx change is required and none is relied upon — that is the whole point: **our receipts no longer depend on the fragile shared `/receipt/` block at all**, so no future FrictionAI-side nginx edit can break us.
**Why not the alternatives:** (a) *Re-point nginx each time* = the band-aid that caused the ping-pong; rejected. (b) *Host-based routing (a dedicated subdomain → :3005)* is the textbook fix but needs DNS + a cert + a real domain; deferred — the path move gives the same isolation with zero infra. (c) *Change FrictionAI's path instead* requires a cross-repo change we don't control; the `/api/receipt/` move is **unilateral** — we fix our side without touching theirs.
**Consequences:** Receipt display is now collision-proof by construction. `checkDash` gate + `private, no-store` are unchanged (same handlers, extra mount path). CSP/no-store still applies (`/api/receipt/*` matches the existing `/api/` prefix in `lib/security-headers.js`). Tests assert both paths serve identically (`tests/receipt.route.test.js`). If FrictionAI is ever retired or the box stops being shared, this remains correct (a path is a path). The MEMORY_LEDGER runbook is retained for diagnosing any *other* future route mishap on the shared box.

## ADR-026 · Error tracking (#12 Phase 2) = platform log-drain first; Sentry optional, DSN-gated, PII-scrubbed
**Date:** 2026-07-08 · **Status:** Accepted (Owner: Jeevan). Plan: `docs/ops/2026-07-08-operationalisation-plan.md` (#12). Follows Phase 1 (structured stdout logs, `lib/log.js`, PR #138).
**Context:** SYSTEM_COMPLETENESS #12 asks for error *tracking* (aggregation + grouping + alerting), beyond Phase 1's one-JSON-line-per-error to stdout. The obvious tool is Sentry (`@sentry/node`), but it collides with three standing constraints: the **two-deps ethos** (ADR-012 — every new dep is a deliberate exception), **ADR-002 no-PII** (receipts are financial PII; Sentry's default capture — request bodies, headers, breadcrumbs, `sendDefaultPii` — would egress that to a third party), and the **per-client model** (ADR-020 — one instance per client; a shared Sentry project would co-mingle clients). Meanwhile, once hosted (ADR/#7), Render/Fly **already capture stdout/stderr**, so the Phase-1 JSON error lines are aggregatable with *no code and no new dependency*.
**Decisions:**
- **Default path = platform log-drain + alert rules, no new dependency.** Ship the host's captured stdout/stderr (already structured JSON from `lib/log.js`, `level:"error"`) to a log service via the platform's native log-drain (Better Stack / Logtail / Grafana Loki), with an alert rule on `level=error` rate. This gets grouping + search + alerting **out-of-process**, and inherits Phase-1's scrub-by-construction (msg + scalar route context only — never bodies/PII).
- **Sentry is OPT-IN, DSN-gated, default OFF.** The base image stays dependency-free unless a client explicitly enables it: initialise Sentry **only when `SENTRY_DSN` is set** (lazy `require`, so `@sentry/node` is an *optional* dep never loaded otherwise). One DSN/project **per client** — never a shared project (ADR-020).
- **When Sentry is on, PII-scrub is mandatory, not optional (ADR-002 hard rule).** `sendDefaultPii: false` + a `beforeSend` allow-list matching `lib/log.js`: keep error type, stack, route, method, status; **drop** request/response bodies, `merchant`/receipt fields, card data, and any header carrying a token/secret. A scrub test gates the wiring the same way isolation tests gate auth (ADR-025 / SEC).
- **Alert channel reuses what we have** — the Telegram bot or email; no new notification stack.
**Consequences:** #12 Phase 2 needs **zero new dependency** in the default case; error tracking becomes a per-client config choice (log-drain always; Sentry only for a client who needs rich exception grouping/breadcrumbs and accepts the scrubbed third-party egress). No code lands with this ADR — it records the approach; the Sentry adapter + scrub test are written only when a client opts in. Revisit if operating many clients makes per-project Sentry administration heavy (then reconsider a single self-hosted GlitchTip/Sentry with per-client tenancy).

## ADR-025 · Security posture + hardening launch-gate for the business layer
**Date:** 2026-07-07 · **Status:** Accepted (Owner: Jeevan). Audit: `docs/specs/2026-07-07-security-hardening-audit.md`. Trigger: Owner security directive + *Vibe Coder Security Checklist* + a file-storage video.
**Context:** M2 adds auth roles, cross-branch isolation, file storage, and more untrusted input — concentrating new risk. Owner: "no hackers can hack us, no raw data can infiltrate/inject our DB, make sure RLS are all there," rate-limiting present but generous for the first client.
**Decisions:**
- **Defense in depth, four layers:** (1) **physical per-deployment isolation** (managed silos, ADR-020 — cross-company leak impossible); (2) the single **`scopeForUser` bouncer** for within-company branch scoping; (3) **RLS + service-role mediation** at the DB (anon denied on every table); (4) validation / rate-limiting / strict CSP at the edges.
- **RLS everywhere is a hard rule:** *no new table ships without `enable row level security`* and no permissive anon/public policy (verified 5/5 on `schema.sql`). **Honest caveat:** the service-role key bypasses RLS, so RLS guards against direct/anon DB access — within-company branch isolation is the app-side bouncer (tested), with **JWT-scoped RLS on the roadmap** (belt-and-suspenders).
- **No SQL injection by construction:** no string-built SQL anywhere; PostgREST values are `encodeURIComponent`-escaped and treated as data; RPC args parameterised. Untrusted OCR/model text is "caged data, never instructions."
- **Files never in the DB (video = our ADR-018):** blobs → private Supabase Storage bucket (object storage) + CDN; the DB stores only the `receipt_url` string. Add magic-byte upload validation + keep the bucket private (signed/proxied reads).
- **Rate limiting = on everywhere, generous for the first client** (env-tunable caps); only *failed* auth is throttled, never valid traffic.
- **A launch-gate hardening backlog (SEC-1…SEC-10)** is folded into the plan as a **Security Gate applied to every phase** — the ⚠️/**yes** items must close before any paying-client instance goes live (password policy, server-side role gating + isolation tests, file-upload validation, business offline-cache handling, M2 input validation, security logging, per-route rate limits, RLS on all new tables, dependency scan in CI).
**Consequences:** No single new dependency; mostly discipline + tests + a few small guards. Security review of the M2 auth/isolation code is **Tier-2** (independent cross-review, never self-merge). Remaining true gaps are operationalisation (hosting/HTTPS, monitoring, log-aggregation, CI dependency scan — 16-layer #7/#12/#13/#8).

## ADR-024 · `pdfkit` (pure-JS) for the Petty Cash Statement PDF export
**Date:** 2026-07-07 · **Status:** Accepted (Owner: Jeevan) — CTO decision, Owner brief "we want the exact export of a PDF, just like the sample". Implements the PDF half of ADR-023. Spec: `docs/specs/2026-07-06-petty-cash-statement-format.md` §3.
**Context:** ADR-023 requires a **PDF** statement that is pixel-faithful to the client's filed output (styled table — red title, blue headings, grey/ yellow/ green fills, borders, sign-off block) **followed by the appended receipt pages**. Our existing tools can't produce it: `exceljs` writes `.xlsx` only; `@hyzyla/pdfium` *reads/rasterises* PDFs but cannot author them. We need a PDF **writer**.
**Decision:** Add **`pdfkit`** — a pure-JavaScript PDF generation library (MIT, **no native binaries**). It draws the styled statement (rects/fills/borders/text to match §2b) AND embeds receipt images as pages. Source receipts that are themselves PDFs are rasterised page-by-page via the existing `@hyzyla/pdfium`, then embedded — so `pdfkit` + `pdfium` cover every receipt format (image or PDF, single- or multi-page).
**Why pdfkit over the alternatives:**
- **vs `pdf-lib`:** both are pure-JS; pdfkit's higher-level text/table primitives mean far less hand-written layout code to hit the fidelity bar. (pdf-lib is a fine fallback if pdfkit's transitive-dep weight is ever a concern.)
- **vs hand-rolling a PDF writer (no new dep):** a styled table with fills/borders is tedious and fragile to emit by hand; the "exact as the sample" requirement makes false economy of saving one pure-JS dep.
- **vs `sharp` (rejected, ADR-014):** different category — `sharp` is a *native* image lib (build/binary risk); `pdfkit` is pure-JS, so it honours the "no native binary / no build step" constraint.
**Consequences:** Runtime deps go from `express, dotenv, exceljs, @hyzyla/pdfium` → **+`pdfkit`**. Still pure-JS, still no build step. Only exercised on the `pettyCash`/statement path (a business feature), though it installs for all deployments (normal dependency). **Tier-2** (produces financial documents). Revisit only if a lighter writer becomes necessary. Personal product behaviour unchanged.

## ADR-023 · Company dimension + petty-cash/claim model + Petty Cash Monthly Statement (dual Excel/PDF export)
**Date:** 2026-07-06 · **Status:** Accepted (Owner: Jeevan) — CTO calls confirmed. Extends ADR-021/022. Format spec: `docs/specs/2026-07-06-petty-cash-statement-format.md`. **Confidential source samples** kept out of the repo (real company/staff/bank data); design anonymised.
**Context:** Premala's actual deliverable (from two real sample files) is a **Petty Cash Monthly Statement of Account** — one per **company × branch × month** — with the **receipt snapshots appended one per page**, currently hand-built in Excel (broken `=#REF!` formulas + a sign error) and emailed over WhatsApp. Premala also operates **multiple companies** (legal entities), each with its own branches, categories, and petty-cash floats.
**Decisions:**
- **Add a COMPANY dimension: Group (`account_id`) → Company → Branch → Staff.** New `companies` table; `branches.company_id`; expenses carry `company_id` (derivable from branch, denormalised for reporting). One admin manages all their companies from one instance (Owner: "add a company level"). Each company owns its **own category set** (chart of accounts) via the FieldSpec (#12) — the two samples had 9 vs 5 categories, confirming per-company shape.
- **Petty-cash FLOAT is admin-editable per branch per month** (including the admin's own Head-Office branch — Owner's explicit call). Section A ("cash in-hand") = Balance-B/F + float top-ups.
- **Claim = the maths, not a manual list.** `Balance = Cash-in-hand − Expenditure`; when a branch's running expenses exceed its float (balance goes **negative**), the overspend is a **claim** owed to the staff who paid out of pocket. Computed from the running balance (+ a per-expense `claim_override` for exceptions), never a stored truth that can drift. Reimbursement rides the existing **Phase 4 `payment_status`** (pending → paid). Sign-off maps to roles (Prepared = clerk, Checked/Approved = admin), dovetailing with ADR-022 "Send to Admin".
- **BALANCE sign = correct accounting (CTO call):** positive = surplus/carry-forward (no claim); negative = claim. Their sample's `−75.09` (vs the true `3000 − 2924.91 = +75.09`) is a **manual error we deliberately fix** — computing what their sheet gets wrong is a feature, not a compatibility gap. Optional per-client "match their exact convention" toggle, OFF by default. **Never reproduce `#REF!`** — real computed subtotals.
- **Dual export, both required (Owner: "must have both options, as accurate as the sample"):** **Excel** (`exceljs`, ADR-012 — real totals, embedded receipt thumbnails per ADR-018/021) **and PDF** (statement page(s) + one appended page per receipt image). PDF render approach chosen at build time, **reuse-existing-deps-first** (`@hyzyla/pdfium` already present; `sharp` stays rejected, ADR-014). Excel template = the layout source of truth.
- **New capability flag `pettyCash`** (per-client; Premala = ON). Off ⇒ general product unchanged. All petty-cash/statement queries funnel through the same `scopeForUser` bouncer (now company- + branch-scoped).
**Consequences:** Additive schema (`companies`, `branches.company_id`, `expenses.company_id`/`claim_override`, `petty_cash_floats`, `cash_in`). New plan phases (company dimension → petty-cash floats + claim engine → statement dual export), all flag-gated and Tier-2 (money + schema). Foundation deps already exist (receipt-image storage ADR-018, currency ADR-005, payment_status Phase 4, exceljs ADR-012). No new npm dependency committed yet (PDF-render decided at build). Focus = Premala; the company dimension is a general capability other multi-entity clients reuse.

## ADR-022 · Per-client behaviour = capability-flag PROFILES; Premala (first client) = live data + in-dashboard document hand-off
**Date:** 2026-07-06 · **Status:** Accepted (Owner: Jeevan) — CTO-recommended, Owner-confirmed. Extends ADR-010 (one-codebase flags) + ADR-020 (delivered per-client) + ADR-021 (M2). Client profile: `docs/clients/premala.md`.
**Context:** Premala (our **first client**) doesn't work the way the default M2 "live master aggregate" model assumes. Their real workflow: each **branch keeps its own formatted Excel** (receipt snapshots embedded) which they export **as PDF** in a specific existing layout; today branches hand that file to the admin **manually over WhatsApp / a chat app**; the **admin's "master template" is the admin's OWN file** (HQ/petty-cash expenses the admin captures) — it is **NOT** a spreadsheet that every branch live-merges into. But the admin **does** want **live reports/analysis** on the dashboard. (Owner will supply the exact PDF-export samples; format build is deferred until then.)
**Decisions:**
- **Per-client differences are expressed as capability-flag PROFILES, never a code fork (reaffirms ADR-010/020).** A client profile = a set of `getCapabilities()` flags + a `docs/clients/<client>.md` doc. Hard rule stands: a bespoke request becomes a shared flag/config knob or a flag-gated module — never `if (client === "Premala")`. This is the framework; Premala is the first instance of it.
- **Split the system into a LIVE DATA layer and a DOCUMENT layer, and flag them independently.** The data layer (rows-not-workbooks, ADR-021) is **unchanged**: every branch receipt still flows into the one shared DB, so the admin's **reports/analysis stay live**. What Premala turns off is only the live-editable / live-**merged master spreadsheet** surface — not the live analytics.
- **Premala profile flags:** `multiUser` **ON**; `liveMasterMerge` **OFF** (no all-branches-into-one live master workbook; the admin's master file = their own Head-Office expenses, which they add to themselves); `excelLiteGrid` **OFF** (no in-dashboard live cell-editing); `branchSubmission` **ON** (the "Send to Admin" flow below).
- **New GENERAL feature — "Send to Admin" branch submission (flag `branchSubmission`).** A clerk submits their branch's compiled export to the admin **in-dashboard**; it lands in the admin's dashboard for compile/export. Built as a **reusable, flag-gated** feature (any document-handoff client benefits), NOT a Premala one-off. **Why it's the right call, not just a customisation:** (1) it removes the current **WhatsApp/chat-app hand-off**, which leaks receipts (PII/financial docs) outside every control we've built — keeping it in-dashboard keeps it inside the client's **isolated managed-silo instance** (ADR-020), consistent with our processor/data-privacy posture (ADR-021 §11); (2) it's **cheap** — the rows are already in the shared DB, so submission is a lightweight state-change + admin notification, not a file transfer; (3) it yields a free **audit trail** (who/which branch/which period/when) the WhatsApp flow lacks.
- **Premala's exact PDF export layout (Excel-with-embedded-receipt-snapshots → PDF) is PARKED pending client samples.** Phase 3's receipt-image-in-Excel embed (ADR-021 / ADR-018) is the foundation; the PDF rendering of their specific layout is the only genuinely new build item, and we don't build it blind.
**Consequences:** No fork; Premala ships as the default build with a flag profile. The general MVP roadmap (ADR-021 phases) proceeds unchanged — Phase 1 identity (PR #108) etc. are untouched. Two roadmap additions: (a) the `branchSubmission` "Send to Admin" feature (flag-gated, general) slots in after the data layer exists; (b) a client-specific PDF export-format task, blocked on Premala's samples. New flags (`liveMasterMerge`, `excelLiteGrid`, `branchSubmission`) join `getCapabilities()` (default = general product behaviour; Premala overrides). No new npm dependency implied yet (PDF-of-Excel rendering approach decided when samples arrive — reuse existing `@hyzyla/pdfium`/`exceljs` where possible before adding anything).

## ADR-021 · M2 business-account layer — server-guard auth now (RLS later), rows-not-workbooks, clerks-only bot
**Date:** 2026-07-06 · **Status:** Accepted (Owner: Jeevan) — design signed off section-by-section. **Tier-2** (auth + DB schema + cross-branch isolation). Spec: `docs/specs/2026-07-06-business-account-multibranch-design.md`.
**Context:** A client whose business has an HQ + multiple branch offices (each a clerk who captures receipts, plus staff who hand them over) needs the deferred M2 multi-user layer (MUGI.md §5). The prior CTO note (Owner's planning PDF) correctly picked "System 3" (shared Postgres + roles) over local-file / Google-Sheets designs. This ADR records the CTO-simplified shape landed for a ship-soon build. M2 stays a **per-client option** (ADR-010/020), not SaaS multi-tenancy.
**Decisions:**
- **One `account_id` = one client business; branches/staff are dimensions INSIDE it** (new `branches` + `users` tables; `branch_id`/`staff_user_id` on `expenses`) — NOT one account per branch. The admin's "live master view" is then a single-scope `GROUP BY`, not a cross-account join. Everything is already `account_id`-scoped (`lib/supabase.js` auto-inject), so this is additive.
- **Rows, not workbooks (the anti-tangling decision).** Exactly ONE data shape per client — the FieldSpec (#12) — and it is **HQ-owned**. Staff contribute rows, never columns. The "master template" is a query over the one `expenses` table, not a stored/synced file; a "branch workbook" is just `buildWorkbook()` on filtered rows. Staff Excel imports are **mapped into** the canonical FieldSpec (`parseTemplate` CANON aliasing); unmappable → `ai_raw`/remark; bulk "import data back" is **blocked**. Shape-mismatch/"tangling" is therefore impossible by construction (directly answers the Owner's flagged concern).
- **Credentialed roles = HQ Admin (1) + Branch Clerk (1/branch, auto-gen creds).** "Staff" = a name directory for attribution — **no dashboard login, no bot binding** (Owner's cost/efficiency call). Anomaly "staff decides first" therefore means the **clerk** decides first; admin overrides.
- **Admin is ALSO a capturer, not just an overseer (Owner, 2026-07-06):** HQ has its own petty-cash receipts to audit, so the **HQ admin gets the dashboard upload + a Telegram bot binding** (amends the earlier "clerks-only bot" — now **admin + clerk are bot-bound; staff still are not**). Modelled cleanly by treating **HQ as a "Head Office" branch** (auto-created on setup): the admin's binding/uploads scope to it and flow through the same rows/master/export. Admin *reads* still span all branches. **Anomaly carve-out:** for Head-Office items the admin is the first decider (no clerk beneath them) — the "admin can't originate" rule governs only branch/clerk items.
- **Auth = lighter server-guard now, RLS later (CTO call for a next-week ship).** `crypto.scrypt` password fingerprints (**no new dependency** — Node core, honours the two-deps ethos); opaque session tokens reusing the existing `checkDash` `Authorization: Bearer` plumbing (swap fixed-token compare → session lookup resolving `{account_id, branch_id, role}`); **one central `scopeForUser` "bouncer"** funnelled through the `lib/supabase.js` helpers filters every query by role/branch. **Honest limitation:** until DB-level RLS is on, isolation is a *policy* enforced by that one tested choke-point, not a database wall — a scoping bug could leak cross-branch data. Mitigation = single choke-point + isolation tests; **JWT-scoped RLS stays on the roadmap** as belt-and-suspenders (schema template already in `schema.sql`).
- **Bot = a clerk tool.** First contact `/start <one-time-token>` binds `chat_id → clerk/branch/role`, locked (reuses `docs/specs/2026-07-03-user-onboarding-chatid-linking-design.md`) — this is the honest form of the PDF's "one-click Telegram auto-login" (one tap + one Start, not zero-tap, which Telegram forbids) and doubles as the CIO section's "lock role on first access." Upload → "which staff?" tag (remember-last default); personal-expense approve gate (existing detector); categories from the FieldSpec; simplified today's-bills → single Delete → "enter number" → "deleted"; branch-scoped; weekly = Sun–Sat.
- **Anomaly: staff-first + admin safety valve** — admin can override but not originate a decision, **except** after `ANOMALY_VALVE_DAYS` unresolved (default 3) so the queue can't freeze. **Payments:** per-receipt `payment_status` (pending default / paid), **admin edits / clerk views**, with filtered **bulk mark-as-paid** (chunked per the Bill.com 200-cap lesson; QuickBooks Online notably lacks bulk-pay, so this is a quality edge). **Excel-lite v1** = inline cell-edit + autosave (values only, **no column changes** — preserves anti-tangling); full spreadsheet = fast-follow.
- **Receipt image is a first-class audit output (Owner "very important", 2026-07-06):** durable receipt-image storage (**ADR-018**, private Supabase `receipts` bucket, `receipt_url`, both ingestion paths) is a **required prerequisite** for business accounts — it makes images permanent (not the rot-prone live Telegram `file_id`) and viewable on the dashboard. **The Excel export EMBEDS the receipt image per row** (`lib/excel.js` via exceljs `addImage`) + a hyperlink to full-res, so the exported `.xlsx` is self-contained for offline audit. Default = embed display-scaled thumbnail; **links-only** fallback for very large exports (no image-resize dep — `sharp` rejected per ADR-014). Blank cell when a row has no image. **NOT business-gated — the Receipt embed applies to PERSONAL exports too** (general `lib/excel.js` enhancement, personal-first); only the Branch/Staff columns are business-only. May ship on the personal product independently of the M2 epic.
**Consequences:** No merge engine / file-sync / stored master workbook. Reuses `lib/reports` (add branch/staff dims), `lib/excel` (`buildWorkbook`), `lib/anomaly`+`routes/review`, `lib/categorize`, `lib/bot`, `checkDash`, `account_settings`/`getCapabilities`. New: `lib/auth.js`, `lib/branches.js`, `routes/{auth,branches}.js`, schema (`branches`/`users`/`sessions`/`bot_bindings` + expense columns). New per-client operational risks to own before onboarding a paying client: dedicated Supabase project per client (ADR-015), paid Groq capacity under multi-branch bursts (ADR-016), durable Supabase Storage for business receipt images. Phased build (identity → provisioning → data dims → anomaly/payments → bot → frontend); each phase TDD; Tier-2 cross-review before merge.
- **Delivered as an isolated instance per client company (ADR-020): one codebase, N deployments.** Every client difference is a **config/data surface** (template/categories, branding in `account_settings`, capability flags via `getCapabilities`, currency/valve-days/`max_branches`/chunk) or a **per-instance secret** (own Supabase project + Telegram bot token + Groq keys) — **never a per-client code fork.** Hard rule: a bespoke request becomes a shared config knob or a flag-gated module, never `if (client === "X")`. **Isolation is by deployment (separate DB per company), not row-scoping** — which bounds the §6/app-side-scoping caveat to *within-company* (branch-to-branch) and never *cross-company*, a further reason the RLS-deferral is acceptable for v1. Spec §10.
- **Hosting DECIDED (CTO call) = managed silos, operated by us.** We host/patch/back-up every instance; the client touches nothing (solution-provider value prop). Each company = its own hosted instance + own Supabase project + own bot token → **physical cross-company isolation** (no shared DB), strongest possible and keeps the current service-role architecture + fast auth intact. Onboarding = a provisioning script, not code. **Pooled multi-tenant was considered and deferred:** it's cheaper only at large scale and would make RLS the single wall — and critically, since the app uses the **service-role key that bypasses RLS today**, "just turn on strong RLS" is *not* sufficient; pooling would require re-architecting company-scoped access onto Supabase-Auth + **JWT-scoped RLS keyed on `account_id`**. **Forward-compat is free:** `account_id` already exists on every table and auto-injects, so each silo *is* one tenant and a future pooled migration is structurally open without new schema. This **reaffirms ADR-020** (isolated per-client delivery), now clarified as *we-host-it-all managed silos*, not client-self-hosted.
- **Data-privacy / client-trust posture (spec §11):** as data *processor* we answer breach/privacy questions on technical controls (physical per-company DB isolation, TLS + at-rest encryption, least-privilege, ADR-002 log posture, export/delete-on-exit) + contract (DPA + ≤72h breach clause) + transparency (sub-processor disclosure). **OCR provider is a per-deployment config knob** (`lib/groq.js` boundary): default Groq with zero-retention/no-training terms; regulated clients escalate to a DPA-backed provider (Azure OpenAI / Bedrock / Vertex or managed OCR) — self-hosted OCR only for air-gapped mandates. **Pre-sale gaps to close (ADR-015 ladder):** company-owned paid Supabase org (one project/client, backups, region), legal entity, DPA + data-handling summary, breach runbook, operator hygiene (MFA/company-email/password-manager/named-access-register). **Domain is not technically required** (free host subdomains + bot webhook suffice); at most one ~$10/yr company domain serves all clients via subdomains, or the client uses their own — never one paid domain per client.

## ADR-016 · Groq multi-key rotation (free-tier quota pool) — random selection across N accounts, 429-driven fall-through
**Date:** 2026-07-03 · **Status:** Proposed (Owner: Jeevan) — **pending Barat sign-off (touches his frozen `lib/groq.js`, ARCHITECTURE §3.2)**
**Context:** The whole system runs on ONE Groq free-tier account (Barat's). Free tier is per-account rate-limited (RPM) and daily-capped (RPD — ~14.4k/day on common instant models, lower on vision). A single account is both a hard ceiling and a single point of failure for AI availability. Pooling several team accounts' quotas (Barat's + Jeevan's ×2 + Mugi's) ~multiplies the free daily ceiling at $0.
**Key correctness fact (why this is safe, not a hack):** a Groq API key is a *billing credential*, not a model selector. The same `model` id routes to identical weights regardless of which key pays. **Switching keys does NOT change the model/prompt/temperature/output quality** — zero "gets dumber as it falls through." That degradation only happens if you switch to a *cheaper model*, which we explicitly do NOT do. This is pure quota multiplexing on the same model; N separate accounts each within their own free limits is standard practice, not evasion of any single account's limit.
**Decision:** Add a **random-selection key pool**. `.env` gains `GROQ_KEYS=key1,key2,...` (comma-separated); **backward-compatible** — unset → falls back to today's single `GROQ_KEY`, behavior identical. New tiny module **`lib/groqkeys.js`** (Jeevan): `pickKey()` random, `nextKey(tried)` random-from-untried, pure/no-state. Barat's `lib/groq.js` retry loop starts on a random key; on **429** it retries a **different** random key with **no sleep** (a fresh account's quota is untouched); only when **all** keys 429 does it fall to today's backoff. Non-429 errors unchanged. **Random** (not round-robin) per Owner's call 2026-07-03 — spreads normal load evenly, no fairness bookkeeping.
**Ownership:** `lib/groqkeys.js` + tests = Jeevan; the `lib/groq.js` call-site change = Barat (his frozen file → sign-off first, same as ADR-007). **Tier-2** (multiple third-party secrets). Security: pool holds multiple plaintext keys — never logged, never client-sent (server-only, unchanged), rotated per ADR-015's launch gate; a pool leak exposes N accounts vs 1 (accepted pre-launch on host-only secrets).
**Consequences:** ~Nx free daily AI ceiling for $0; graceful degradation to backoff only when the whole pool is exhausted; one small Jeevan module + a small Barat call-site change; config-driven (add/remove keys = edit `.env`). Model quality unchanged. Spec: `docs/specs/2026-07-03-groq-key-rotation-design.md`. Revisit at paid-tier migration (ADR-015 ladder).

## ADR-015 · Supabase custody: personal free tier (pre-incorporation), bounded by backup + disclosure + rotation — not a privacy breach, not yet "company infra"
**Date:** 2026-07-02 · **Status:** Accepted (Owner: Jeevan)
**Context:** The product's only database is a Supabase project on Barat's personal account, free tier. There is no registered company entity, no company domain/email, and therefore nothing exists yet to legally "own" a company Supabase org — this is normal for a pre-incorporation MVP, not a gap unique to this project. The real question raised (Owner + Claude discussion, 2026-07-02) was whether this constitutes a data-privacy risk, and if so, what actually mitigates it — as opposed to what merely *sounds* like it does.
**Analysis (corrected from an earlier overstated framing this session):**
- **This is NOT a privacy/security breach.** A breach means unauthorized access occurred; nothing here does that. The actual privacy controls — encryption in transit/at rest (Supabase default), RLS, service-role-key-only backend access (`lib/supabase.js`), the browser never touching Supabase directly (CLAUDE.md/ARCHITECTURE §1) — are already in place and are independent of whose email owns the account.
- **Adding a second Owner (Jeevan) to the Supabase project does NOT make it "the company's" infrastructure.** It mitigates exactly one thing: single-person lockout (Barat loses access / is unreachable / leaves). It does not change legal ownership, does not satisfy ToS-as-a-business concerns, and should not be represented as more than a bus-factor fix.
- **The two risks actually being carried are:** (1) bus-factor/continuity — one person's account/credentials are a single point of failure for data availability; (2) no legal entity yet — nothing is "the company's" in a strict sense, which is the normal, accepted state of a pre-incorporation MVP, not a violation to fix urgently.
**Decision — bound and disclose the risk rather than claim to eliminate it (which isn't possible pre-incorporation):**
1. **Independent backup** — Jeevan holds a `pg_dump` (or equivalent export) outside Supabase entirely, refreshed periodically. This is the actual data-loss insurance — it protects against Supabase itself suspending/pausing/purging the project, which multi-owner access does not.
2. **Multi-owner access** — Barat adds Jeevan as a second Owner on the Supabase project (free, ~5 min). Fixes the lockout scenario specifically; claimed for nothing more.
3. **User disclosure** — any real user (including early beta/friends) is told plainly this runs on early-stage developer infrastructure, not yet a registered company. This is what converts an undisclosed risk into an informed, accepted one — the disclosure is the actual control, not the account type.
4. **Key-rotation launch gate (hard blocker, tracked in `docs/STATUS.md` Blockers):** no real user is onboarded until every secret (Supabase service-role key, Groq key, bot token, `DASHBOARD_TOKEN`) has been rotated *after* its last dev-context exposure (shared, committed, pasted, screen-shared) — production must run on secrets that have only ever touched the host — **and** an independent backup (item 1) exists. Fail either → cannot launch.
5. **Tier ladder (Owner-set, recorded here so it isn't re-litigated):** stay on free/personal until ~5 real users or capacity pressure → upgrade to Supabase Pro, billed to/via Barat's account, Owner reimburses, treated informally as the company account → migrate to a company-owned org once a domain/company email exists (re-apply `schema.sql`, migrate data, rotate keys again per item 4).
**Consequences:** No architecture or code change. This ADR exists so the custody arrangement is an explicit, on-the-record decision rather than an implicit assumption — if a dispute or incident ever occurs, there is a clear record that the arrangement was deliberate, bounded, and had backup/disclosure/rotation controls, not negligence. Re-visit this ADR (supersede or close) once the company Supabase org migration (tier-ladder step 5) actually happens.

That was a **mis-scan** — the MCP connector was authed to Jeevan's OWN Supabase org and inspected `fziaxuhonvrhqjulhcyu` (Jeevan's CRM bot), NOT Barat's actual receipt-analyser project (`xurnpvesgcybrnilxszf`, which the connector has no access to). ## ADR-014 · PDF ingestion (#1) rasterizes via `@hyzyla/pdfium` (WASM PDFium) — not MuPDF, not a system binary
**Date:** 2026-07-02 · **Status:** Accepted (Owner: Jeevan) — **LOCKED: spike PASSED (J1, in-session 2026-07-02); fallback not needed**
**Context:** #1 accepts PDFs (digital + scanned, untrusted) on both surfaces. Groq vision reads **images, not PDFs** (ADR-007: qwen is image-only), so a PDF must be **rasterized to page images**, which then feed the existing #7 `runBatch` spine unchanged (page images == `runBatch`'s `images[]`; multi-page and multi-receipt-per-page fall out for free). The only real decision is *how* to rasterize under the project's hard constraints: **no build step, minimal deps, pure Node 22, commercial SaaS (license matters), hostile input.** Options weighed:

| Approach | License | Build step | Deps | Notes |
|---|---|---|---|---|
| **A. `@hyzyla/pdfium`** (WASM PDFium) | **MIT wrapper / BSD-Apache core** ✅ | none (WASM) | **1**, zero-dep | Chrome's PDF engine; renders native+scanned; WASM sandbox |
| B. `mupdf` (official, WASM) | **AGPL or paid commercial** ⚠️ | none (WASM) | 1 | highest fidelity, but AGPL network-service copyleft ⇒ must open-source or buy a license |
| C. `pdf.js` + `@napi-rs/canvas` | Apache-2.0 + MIT ✅ | none (prebuilt) | **2** (one native `.node`) | permissive but platform-specific native binary; JS renderer (slower) |
| D. system binary (poppler/ghostscript) | — | **host install** ❌ | 0 npm | fragile Windows↔Linux, deploy burden, shell-out on hostile input |

**Decision:** Use **A — `@hyzyla/pdfium`**. Rationale: (1) **License is clean for a product we sell** — permissive, no copyleft; **B is disqualified** while a permissive equal exists (AGPL would obligate source release or an Artifex commercial license for our SaaS). (2) **Best fit for "no build / pure Node"** — pure WASM, no native compile, byte-identical on Windows dev and the eventual Linux host; C's `@napi-rs/canvas` works but pulls a platform-specific native binary (the thing most likely to break a deploy). (3) **One zero-dependency package** vs C's two; the WASM blob vendors in, so bus-factor risk sits on a thin JS wrapper, not the renderer (the renderer is the same C++ core shipped in Chrome). (4) **WASM sandbox** (memory-isolated, no shell) is a genuine security win on hostile PDFs — the reason D was rejected. New dep on an **untrusted-input parsing surface** ⇒ **Tier-2** (SOP §4.7, ADR-012 precedent): its own ADR (this) + independent QA before merge.
**Pre-commit check (honest risk):** confirmed from the live API — `@hyzyla/pdfium` is **ESM** (this repo is **CommonJS**), so `lib/pdf.js` loads it via dynamic `import()`; and `page.render()` yields **raw RGBA** (`{data,width,height,channels:4}`), not PNG — the vendor example encodes with **`sharp`**, a heavy native dep we **reject** (it would negate the zero-added-native-deps rationale above). Instead we pass a custom `render` fn that encodes RGBA → **PNG via Node's built-in `node:zlib`** (~40-line in-module helper, no dependency). **Spike result (J1, in-session 2026-07-02):** all of this PASSED on generated native PDFs — dynamic `import()` from CJS works; `PDFiumLibrary.init()` + `page.render({scale, render})` returns `{data,width,height}` RGBA; the `zlib` encoder produced a **legible** PNG (a 300×200pt page at `scale=150/72` → 625×416px, ~9.7 KB); multi-page (3pp) worked; `loadDocument` on non-PDF bytes throws `"File not in PDF format or corrupted"`; init+render ~94ms; `npm install @hyzyla/pdfium` = **"added 1 package"** (zero-dep confirmed). **Fallback = C** (`pdf.js` + `@napi-rs/canvas`) is therefore **not needed** — retained only as a documented contingency. Remaining open item for Barat: confirm the exact error string for a *password-protected* PDF (needs a `qpdf`-generated fixture) so `ENCRYPTED` maps distinctly from `CORRUPT`.
**Consequences:** **Exactly one** dependency added to `package.json` — the WASM `@hyzyla/pdfium` (lands with `lib/pdf.js`, Barat's lane); PNG encoding stays in Node core (`zlib`), no `sharp`. All render knobs env-driven (`PDF_RENDER_DPI`, `PDF_MAX_BYTES`; page cap reuses `MASS_MAX_IMAGES`), so tuning is config not code. Design: `docs/specs/2026-07-02-pdf-ingestion-design.md`; plan: `docs/plans/2026-07-02-pdf-ingestion.md`. Precedent (ADR-012/013) reaffirmed: a new dep gets justify-then-ADR-then-Tier-2-review.

## ADR-005 · Currency conversion is NOT an LLM task
**Date:** 2026-07-01 · **Status:** Accepted
**Context:** #10 needs accurate FX rates.
**Decision:** Use an FX rate API (Frankfurter / exchangerate.host — final choice in §10) with a daily cache; the LLM only detects the source currency (already in OCR). Store `amount_original`, `currency_original`, `fx_rate`, and converted `amount`/`currency`.
