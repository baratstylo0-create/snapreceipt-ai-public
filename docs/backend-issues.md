### 1. "Ask your admin" message shown to personal (non-business) accounts
- File: `lib/bot.js` — `bindWithToken()` (~line 164), `BUSINESS_UNBOUND_MESSAGE` (~line 240)
- Issue: link-binding error messages ("not valid" / "expired" / "already used") all say "ask your admin" — written for the multi-staff business bot. Personal accounts have no admin; every user owns their own account.
- Root cause found (2026-08-22): NOT actually a wrong-message-per-account-type bug. `bindWithToken()`'s own `bind_token` lookup (`sbSelect`) was scoped to `account_id=cfg.ACCOUNT_ID` (the old shared bucket). Every personal signup since 2026-08-14 gets its own unique `account_id`, so this lookup could never find a real, valid connect link for any of them — it fell through to the generic "link isn't valid" message regardless of account type. The message text itself was never the bug.
- Fix applied: `bindWithToken()`'s lookup (and its `chat_id`-set write) now use `sbSelectGlobal`/scoped-write (`lib/supabase.js`), matching every other identity-lookup fix from the same investigation (see `lib/supabase.js`'s `sbSelectGlobal` doc comment). Verified live against a real production account (baratstylo0, chat_id 1376793145) — was resolving to zero rows before, resolves correctly after.
- Status: FIXED (commit on `fix/stale-test-expectations-2026-08-12`, merged into this branch's history; deployed to snapreceiptai.friction.com.my and live-verified)

### 4. Duplicate-receipt detection not triggering on re-upload
- File: `lib/ocr.js` — `loadHistory()` (~line 33), `assembleExpense()` (~line 432); `lib/anomaly.js` — `findDuplicate()` (~line 74)
- Issue: re-uploading an already-saved receipt should hit the existing exact-match duplicate check (merchant+amount+date) and get rejected — a live test saved it as a new entry instead.
- Real root cause found (2026-08-23, on a second, deeper pass): the 2026-08-22 write-up above blamed a missing/unparseable date, which was real but secondary. The ACTUAL cause is the same account-isolation bug pattern found everywhere else this session, just not yet found in this function: `loadHistory()` called `sbSelect('expenses', {...})` with **no `scope`/`account_id` at all**, so it always queried the old shared `cfg.ACCOUNT_ID` bucket — the exact same bug the 2026-08-14 insert-side fix (`assembleExpense`'s own "SECURITY FIX" comment, a few lines below `loadHistory`) had already fixed for the WRITE but never for this READ. For every migrated personal account (its own unique `account_id`), that meant `history` was **always an empty array** — duplicate detection, the exact-file-resend check, and outlier detection were all silently comparing every new receipt against nothing, every time, for every personal account created since 2026-08-14.
- Fix applied:
  1. `loadHistory(accountId)` now accepts the account_id and scopes its query to it — `assembleExpense` passes through the exact same `account_id` it's about to stamp onto the new row, so history always reflects the account the receipt actually belongs to (falls back to the old unscoped/shared lookup when no account_id is supplied, matching `stampScope`'s own default for business/legacy callers — zero behavior change there).
  2. `findDuplicate()` (`lib/anomaly.js`) also hardened per the original 2026-08-22 finding: a missing/unparseable date on EITHER side of the comparison no longer bails out of duplicate detection entirely — it now falls back to a merchant+amount-only match in that case, rather than silently skipping the check. (In practice `expense_date` is always parseable by the time a row gets here — `normaliseDate()` never returns null, manual entry validates strict `YYYY-MM-DD` — so this mainly guards old/legacy rows.)
- 8 new tests: 4 in `tests/anomaly.test.js` (unparseable date on the new expense, missing date on the history row, both missing, and a control proving a missing date still doesn't cause a false-positive match against a genuinely different merchant); 2 in `tests/ingest.test.js` proving `assembleExpense` threads the same `account_id` through to `loadHistory` that it stamps onto the row (and passes `undefined` — the old default behavior — when the caller supplies none). Full suite: 2316/2316 passing.
- Status: FIXED (deployed to snapreceiptai.friction.com.my; PM2 stable post-restart, no crash-loop). Real-world hit-rate not yet measured against live re-upload traffic.

### 5. OCR misreads dates even on clear photos
- File: `lib/ocr.js` (same extraction pipeline as #4), `lib/money.js`, `lib/confidence.js`, `lib/config.js`
- Issue: date extraction sometimes fails on well-lit, clear receipts, forcing a manual date prompt.
- Findings (2026-08-22):
  - `normaliseDate()` (`lib/money.js`) silently substitutes TODAY's actual date whenever it can't parse what the model read — no flag, no signal. Flagged as a tension with Barat's 2026-07-21 directive ("never invent/substitute data"); left AS-IS per Barat's instruction not to change this behavior today.
  - `isDatePlausible()` (`lib/money.js`) already existed to range-sanity-check a date that parses but is likely wrong (e.g. a misread year/digit) — was dead code, never called anywhere.
  - Model: this app uses `meta-llama/llama-4-scout` (`lib/config.js` `MODEL_ROUTES.visionDefault`) — a lightweight/free-tier vision model, chosen for cost. `visionEscalate` (meant for exactly this — retry with a stronger model on low confidence) was pointed at the SAME cheap model — no real escalation path existed.
- Fix applied (2026-08-23, Barat: "try to strong the ocr on date reading"):
  - `visionEscalate` now defaults to `openai/gpt-4o-mini` (override via `VISION_MODEL_HEAVY`) — a genuinely stronger paid vision model, confirmed reachable via the account's live OpenRouter key.
  - `extractReceipt()` (`lib/ocr.js`) now calls the now-wired-up `isDatePlausible()` after the normal read; when the date isn't plausible (unparseable OR parses but is out of a sane range), it retries the WHOLE receipt once with `visionEscalate` and uses that result — cost is only incurred on receipts that actually need it, not a blanket increase on every capture. Guarded against double-escalation, an unconfigured/equal escalate model, and a FieldSpec that doesn't even track a date column. A failed escalation call falls back to the original read, never throws.
  - `normaliseDate()`'s "can't read it at all -> today" fallback is unchanged — this only tries harder BEFORE that fallback runs, doesn't change what happens if even the stronger model can't read it.
  - 7 new tests in `tests/ocr.test.js` covering: escalation triggers on an implausible date, never triggers on a good first read, never double-calls when escalate==default, never fires without a date column, keeps the escalated (stronger) read even if its date is ALSO bad, and never throws on an escalation network failure. Full suite: 2287/2287 passing.
- Status: FIXED (deployed to snapreceiptai.friction.com.my; config confirmed live, OpenRouter connectivity to gpt-4o-mini verified against the real production key). Real-world accuracy improvement not yet measured against live traffic — worth revisiting #4 once it has.

### 8. Logged out ("auto refresh -> login screen") minutes after minimizing Chrome (NEW, 2026-08-24)
- Files: `public/js/api.js` (fix), `lib/auth.js` (root cause context, unchanged)
- Reported live: Barat minimized Chrome for a short while (minutes, not hours), reopened it, and the app bounced to the login screen unprompted. Same symptom as the 2026-08-14/08-19 "session persistence" bugs (see `[[project-receipt-saas-session-persistence-fix]]` memory), but those were already fixed and verified live — this is a DIFFERENT cause hitting the same symptom.
- Investigation: `git diff`'d local vs. live `app.js` (byte-identical — the earlier localStorage "remember me" fix for personal accounts IS live and correct) before looking anywhere else. Checked PM2 logs and found repeated `[checkDash session] lookupSession: unexpected response from Supabase` / `The operation was aborted due to timeout` entries interleaved with bursts of real `401 auth_fail` on `/api/reports` etc. — evidence Supabase intermittently hiccups on this VPS. Directly queried (read-only, user's explicit go-ahead) the live `sessions` table for Barat's own account: his session created at 2026-08-24T04:03:01 (valid until 16:03:01, i.e. ~12h left) was abandoned for a BRAND NEW session minted just 19 minutes later at 04:22:31 — proof the browser was forced to re-login on a session that was still valid and un-revoked in the database. Same early-abandonment pattern found 3x in a row on 2026-08-20/21 in the same table.
- Root cause: `public/js/api.js`'s `notifyAuthExpired()` fired on the very FIRST 401 a token-bearing request received, no matter the reason — including a transient Supabase blip that has nothing to do with the token actually being invalid. One flaky response was enough to wipe both storages and force a full re-login, discarding up to ~12h of a perfectly good session.
- Fix applied: `apiFetch`/`fetchBlob` now retry the exact same request ONCE after a short pause (600ms) before treating a 401 as real. A transient blip clears up and the retry succeeds — nothing happens, the caller just gets its data a moment late, no logout. A genuinely dead/expired/revoked token still 401s on the retry too, and THAT still triggers the logout exactly as before — real session expiry is not weakened, only false positives are filtered out.
- 3 new tests in `tests/frontend/api.test.js`: a transient 401-then-200 resolves normally and never logs out (exactly one retry, not a loop); two 401s in a row still logs out (real expiry unaffected); `fetchBlob` gets the same treatment. Full suite: 2319/2319 passing. `public/index.html`'s `api.js` cache-buster bumped (`?v=20260824a`) per the existing cache-busting rule so returning users get the fix immediately, no hard-refresh needed.
- Status: FIXED (deployed to snapreceiptai.friction.com.my; live-verified the new `api.js` is actually being served with the new cache-buster). The underlying Supabase intermittency itself is NOT fixed (out of scope — infra-level, not app code) — this makes the app tolerate it instead of punishing the user for it.

### 7. "That receipt is already gone" on a receipt captured seconds earlier (NEW, 2026-08-23)
- File: `lib/bot.js` — `handleCallbackQuery()` (catpick:/catedit:/del:/dupview:/dupedit:/dupdel:/dupstaff:/delask: branches), `tryResolveBillDelete()`
- Reported live: Barat uploaded a receipt (Bank Islam, RM30.00), got the category picker as expected, tapped a category, and got "That receipt is already gone." — twice.
- Root cause: EVERY expense-by-`id` lookup in `handleCallbackQuery` (8 call sites) and `tryResolveBillDelete` (2 call sites) went through the scoped `sbSelect`, which defaults to `account_id=cfg.ACCOUNT_ID` (the old shared bucket) when no scope is passed — same root cause as items #1 and the earlier account-isolation work, just not yet found in this specific function. A receipt captured under a migrated personal account's own unique `account_id` was invisible to the lookup, so EVERY post-capture button — category pick, edit category, delete, duplicate view/edit/delete, staff picker, and the business bill-delete-by-number flow — was broken for any account with a unique `account_id` (every real personal signup since 2026-08-14). This was the single highest-impact bug found this session: it broke the core capture-to-edit loop, not an edge case.
- Fix applied: all 10 `id`-keyed lookups now use `sbSelectGlobal` (`id` is already a globally-unique primary key, same reasoning as every other identity-lookup fix — see `lib/supabase.js`'s doc comment); the 10 corresponding writes (`sbUpdate`/`sbSoftDelete`) now carry `scope: { account_id: row.account_id }` from the already-fetched row. The real ownership check (`rep_chat_id` match) is untouched. Business-mode staff-assignment writes (`sendStaffPicker`/`startBatchStaffWizard`/`sp:` callback, 5 sites) were NOT touched in this pass — business accounts still share `cfg.ACCOUNT_ID` today (unmigrated), so they're not currently broken; flagged as a follow-up for defense-in-depth consistency (`task_eedee55a`-style — see the separate `routes/branches.js` staff-lookup flag from earlier this session for the same reasoning).
- Verified live against a real production receipt (CAPATI CHENG ENTERPRISE, RM62.80, under Barat's migrated account_id): before the fix this would have hit "already gone"; after, the category picker correctly opened via edit-in-place. The receipt's status was reset to `awaiting_category` as a side effect of this live test and restored to `saved` immediately after — no data lost, category untouched throughout.
- 1 new regression test in `tests/bot.categorypicker.test.js` proving the exact scenario (a receipt under a migrated account's own unique `account_id`, with `sbSelect` deliberately returning nothing, is still found via `sbSelectGlobal`). 6 existing test files (`bot.categorypicker`, `bot.delask`, `bot.delete`, `bot.dupdel`, `bot.duplicate`, `bot.business.todaybills`) updated to mirror their `sbSelect` stub into `sbSelectGlobal`, matching each one's original test intent. Full suite: 2288/2288 passing.
- Status: FIXED (deployed to snapreceiptai.friction.com.my and live-verified against a real production receipt).
