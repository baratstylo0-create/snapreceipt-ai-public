# MEMORY_LEDGER — Receipt Analyser SaaS
> Compact durable memory (lean-context). Load this FIRST on a returning session; don't re-derive.

## What this is
**Delivered, per-client automation SYSTEM** (NOT a multi-tenant SaaS — ADR-020, 2026-07-05): read receipts (photo/PDF) → extract client-templated fields → dashboard + Excel + Telegram bot + Falc agent. Vertical AI track. Under Friction SOP. We build once, deploy/customise an instance per client (their template/categories/branding/features). No self-serve signup / billing / app-store / installer. ALL features stay; only packaging changed. "SaaS phases" (public onboarding, billing, store, marketplace multi-tenancy) flagged N/A; multi-tenant/roles = per-client option. "16-layer" completeness image not yet in repo (pending Owner).

## Architecture (one line each)
- Node 22 + Express, **no build**, deps = express+dotenv (+ approved). Native fetch/Buffer, `hreq()` helper. No axios/node-fetch/multer.
- Supabase Postgres via REST, **service-role server-side only**; browser uses `/api/*`. RLS on, anon denied.
- Vision OCR = **OpenRouter** (`lib/openrouter.js`, `meta-llama/llama-4-scout`, since 2026-07-21, ADR-029). Text/classify/agent chat = still **Groq** (`lib/groq.js`, tiered model routing, backoff on 429).
- Telegram bot + dashboard upload = inputs. `account_id` scopes everything (multi-tenant-forward).
- Being modularized: `server.js` (wiring) + `lib/*` (one concern/file) + `routes/*`. See `docs/ARCHITECTURE.md` §3 frozen interfaces.

## Key facts / GOTCHAS
- **A direct DB cleanup (bypassing the app, e.g. a one-off `sbHardDelete` script over SSH) can make an already-open dashboard tab look "out of sync" (2026-07-22).** It isn't — the delete is real (confirmed via raw REST query), the dashboard tab is just showing client-side state it fetched before the cleanup ran. A refresh fixes it; Telegram never shows this because it re-queries live on every command. After any direct-DB write that skips the app's own API, remind whoever has a dashboard tab open to refresh it — don't chase this as a sync bug.
- **🚨 "STAFF/DATA LOOKS MISSING ON TELEGRAM BUT EXISTS ON THE DASHBOARD" (or vice versa) — CHECK BRANCH BINDING FIRST (2026-07-22, recurred same night as the stale-tab incident above, same underlying cause: overlapping QA-era branches).** Symptom: Staff Lock says "No staff members found" even after staff were added via the dashboard. Root cause: the Telegram chat's `bot_bindings.branch_id` and the dashboard login's `branch_id` are TWO DIFFERENT branches — this account has several similarly-named leftover QA branches (`QA Testing`, `QA Admin 1/2`, `wefsef`, `vaevdfav`, `sdwf`, plus per-feature temp ones like `QA - Barat (temp clerk)`) and nothing in the UI shows which branch a login/chat is actually bound to. **Diagnostic:** query `bot_bindings` for the chat's `branch_id`, then `users` (`role=staff`) for which branch the staff were actually added to — if they differ, that's the bug. **Fix:** use the app's own `lib/branches.js` `addStaff()`/`removeStaff()` (not a raw SQL bypass) to move staff onto the chat's actual bound branch. **Standing risk:** not fixed at the UI level (no visible "which branch is this on" indicator) — will recur on any feature that's branch-scoped until either the leftover QA branches are cleaned up or a branch indicator ships. Both flagged, neither built, Owner has not asked for them yet.
- **🚨 A "FRESH" LOCAL `.env` IS MISSING THIS ACCOUNT'S REAL SETTINGS — CHECK ALL OF THESE FIRST, EVERY TIME (2026-07-21/22, one session, four separate incidents, same root cause).** Symptom pattern: something that should obviously work doesn't — currency shows `$` instead of `RM`, receipts show "0 rows"/"no expenses" on the dashboard even after "✅ Saved", "Edit category" says "already gone" on a receipt that WAS saved, or a business feature (Staff Lock, branches) silently falls through to the generic fallback reply. **Every one of these, this session, traced to the SAME cause: a local `.env` present and loading fine, but missing specific account-critical values** that only reveal themselves as a downstream symptom, never a startup error. Confirmed missing, one at a time, over one session:
  - `DEFAULT_CURRENCY` (defaults to `USD` silently — symptom: `$` instead of `RM`; same failure mode as the historical "all live receipts saved as USD" incident below, just a different host this time).
  - `OPENROUTER_KEY` (required since ADR-029 — without it vision OCR simply can't run).
  - `SB_KEY` — was set to the **`sb_publishable_...`** key, not the **`sb_secret_...`** (service-role) key `.env.example` explicitly documents as required. **This is the big one:** the publishable key let `SELECT`/read calls return `200 OK` with an empty result (RLS silently filtering, not an error) AND apparently still let inserts through in this case — so the dashboard showed "0 receipts" and "Edit category" said "already gone" even though the real data was safely in the DB the whole time. **Don't conclude "0 rows" or "not found" means data loss** — verify with the correct key before telling the Owner anything is missing (this is Problem 3 from `docs/qa/2026-07-17-lessons-learned-review-queue-stafflock-duplicates.md` recurring almost verbatim, on a different local box).
  - `ACCOUNT_TYPE=business` + `CAP_MULTI_USER`/`CAP_COMPANY_DIMENSION`/`CAP_PETTY_CASH`/`CAP_LIVE_MASTER_MERGE`/`CAP_BRANCH_SUBMISSION` — **all six** were absent, so `getCapabilities()` (`lib/account.js`) silently ran the account in **personal mode** even though real business data (branches, staff, the Construction co. category set) already existed in the database. With `multiUser` off, `businessBinding` in `lib/bot.js`'s `handleUpdate` stays `null` forever, so EVERY business-only branch (Staff Lock text-match, branch-scoped commands) is unreachable and silently falls through to the generic catch-all reply — looks exactly like "the button is broken," but the button was never wired up because the account wasn't recognized as business at all. `docs/clients/premala.md` §3 has the exact required flag values for this client.
  - **Diagnostic, cheap, do this before assuming ANY code bug:** `grep -E "^ACCOUNT_TYPE=|^CAP_|^DEFAULT_CURRENCY=|^OPENROUTER_KEY=|^SB_KEY=" .env` and eyeball every line against `.env.example` + `docs/clients/premala.md` §3 — a MISSING line is invisible to `git status` (`.env` is gitignored) and produces NO startup error, only a downstream symptom that looks like a code bug.
  - **After ANY `.env` edit, a restart is required** — dotenv loads `.env` into `process.env` ONCE at boot; editing the file never reaches an already-running process (same lesson as the standing "`.env` move-aside restore can silently no-op" gotcha below, and the historical "all live receipts saved as USD" incident).

- **🚨 `.env` move-aside restore can silently no-op — CHECK BEFORE TRUSTING `.env` IS BACK (caught 2026-07-14).** Found `.env` missing entirely (only `.env.local.bak`, dated **2026-07-09**, present) at the start of a session — meaning some earlier session's `mv .env .env.local.bak && node --test && mv .env.local.bak .env` never actually restored it, and it sat renamed for 5+ days across multiple sessions unnoticed. Root cause: `mv .env .env.local.bak.tmp 2>/dev/null` swallows the error when `.env` is ALREADY missing (e.g. from a previous session's failed restore), so the aside/restore dance silently becomes a no-op instead of failing loud — and since `.env` is gitignored, `git status` never surfaces it either. Went unnoticed this long because (a) hermetic tests (~all 2048) never touch real `.env` values, and (b) live diagnostic scripts happened not to run in between. **Fix used:** verify the backup is genuine before trusting it (`grep`/list its `KEY=` names, don't just check it exists) and restore with `cp` not `mv` (keeps the backup as a safety net instead of consuming it). **Going forward:** after any `node --test` run, confirm `ls .env` succeeds before considering the session's env state clean — don't rely on the mv/restore pair being correct just because no error was printed.
